# 06 数据库层与启动迁移策略

> 文档编号：06
> 项目：Go 版身份核验服务
> 状态：已实现（2026-11-18）
> 证据基线：`internal/adapter/pg/gormmodel`、`internal/adapter/pg/gorm.go`、`internal/store`、`contracts/ddl/001_baseline.sql`

## 1. 决策

- 数据库层采用 **GORM**（单栈），模型即 schema 声明。
- **API 启动时执行 AutoMigrate**；失败则启动失败，不进入服务状态。
- AutoMigrate 只负责**增量**：建表、加列、索引、CHECK、部分索引。
- **删除/重命名/收窄类型**由外部 SQL 执行，版本化到 `migrations/`，不要求 GORM 迭代删除。
- 43 个外键由 **GORM `BelongsTo` 关联 + AutoMigrate** 创建，不再单独维护 `fk_constraints.sql`。
- 10 个原子函数继续使用 SQL（GORM 事务内 `Exec/Raw`），不强行 ORM 化。

## 1.1 关联原型验证

已用临时库验证：

- `BelongsTo` + `constraint:OnDelete:CASCADE` → `FOREIGN KEY (developer_id) REFERENCES developers(id) ON DELETE CASCADE`
- `BelongsTo` + `constraint:OnDelete:SET NULL` + 可空字段 → `ON DELETE SET NULL`
- 自引用 `documents.back_of_id_document_id → documents(id)` → 正常创建
- 复合主键子表 `idempotency_keys(key, developer_id)` 的 `developer_id` 外键 → 正常创建
- 若同时定义正反向关联，GORM 会去重，只生成一条外键

## 2. 启动顺序

```text
加载配置
  → 连接 PostgreSQL
  → 获取 advisory lock（固定 key）
  → 设置 lock_timeout / statement_timeout
  → AutoMigrate(31 models，含 43 个 BelongsTo 外键)
  → 释放 advisory lock
  → 标记 migration_ready=true
  → 启动 HTTP；/health/ready 依据 migration_ready 返回
```

失败处理：

- 任一步失败：记录失败阶段与 SQL 错误，进程退出非 0。
- 不进入“半服务”状态；`/health/ready` 不返回 200。
- 迁移锁未获取到：等待至超时后退出，避免多副本并发改表。

## 3. 多副本与并发

- 所有副本启动时竞争同一 advisory lock；只有持锁副本执行迁移。
- 其余副本在锁释放后重新检查 schema 版本（或直接跳过已完成的迁移）。
- 迁移期间不接收流量；负载均衡以 `/health/ready` 摘除实例。
- 迁移超时必须小于编排层健康检查窗口，避免误判为服务异常。

## 4. 外部 SQL 边界

| 操作 | 执行方式 |
| --- | --- |
| 建表 / 加列 / 加索引 / 加 CHECK | GORM AutoMigrate |
| 外键 | GORM `BelongsTo` 关联 + AutoMigrate |
| 删除列 / 表 / 索引 | 人工审核的 `migrations/` SQL |
| 重命名列 / 表 | 同上；完成后更新模型与基线 |
| 类型收窄 / 可空性变化 | 同上；先 dry-run 评估，再执行 |
| 数据回填 | 独立 SQL 或一次性命令，不写在 AutoMigrate |

### GORM 关联与外键

- 43 个外键统一在**子表模型**上用 `BelongsTo` 定义；反向 `HasMany/HasOne` 只在需要遍历时添加。
- 关联标签必须包含 `foreignKey`、`references`、`constraint:OnDelete:...`。
- `ON DELETE SET NULL` 的字段必须是可空指针；`CASCADE` 字段保持非空。
- 自引用（`documents.back_of_id_document_id`）使用独立关联名与 `foreignKey`。
- 复合主键子表（`idempotency_keys`）的 `developer_id` 关联已验证可用。
- 关闭 `FullSaveAssociations`；禁止用带嵌套结构的 `Save` 隐式写关联；更新显式使用 `Create/Updates/Select`。
- GORM 生成的外键名形如 `fk_<table>_<relation>`，与基线自动名不同；parity 测试按**语义**比较（列、引用表、ON DELETE），或为需要固定名字的约束显式指定 `constraint:<name>,...`。
- 同时定义正反向关联不会重复建外键（GORM 会去重）。

要求：

- 外部 SQL 必须版本化、可回滚、执行前备份。
- 破坏性变更完成后，更新 `001_baseline.sql` 与 parity 测试。
- 禁止在 AutoMigrate 中依赖 GORM 删除或重命名。

## 5. 不变量

1. 模型标签必须完整：`TableName`、`column`、`type`、`primaryKey`、`default`、`check`、索引 `where`。
2. 不嵌入 `gorm.DeletedAt`，避免改变删除语义。
3. 更新布尔/分数等零值字段必须用 `map` 或 `Select`。
4. 10 个原子函数保持 `FOR UPDATE SKIP LOCKED`、CASE upsert 等 SQL 语义。
5. 时间语义：数据库 `NOW()` 与应用 `time.Now().UTC()` 必须统一，禁止混用本地时区。
6. 关联仅用于外键与显式 `Preload`；关闭 `FullSaveAssociations`，禁止隐式级联写。

## 6. 验收门禁

- [ ] 空库启动：31 表 / 329 列 / 43 外键 / 关键索引与 CHECK 生成
- [ ] 43 个外键的引用表与 `ON DELETE` 语义与基线一致（名字可归一化）
- [ ] 重复启动幂等：无重复索引/约束，无类型漂移
- [ ] 两副本并发启动：仅一个执行迁移，另一个正常等待后服务
- [ ] schema parity：AutoMigrate + FK SQL 结果与 `001_baseline.sql` 语义一致
- [ ] 迁移失败：进程非 0 退出，`/health/ready` 不通过
- [ ] 外部删除 SQL：演练一次，验证回滚与基线更新流程
- [ ] 热点接口基准：相对 pgx 不劣化超过 10–15%

## 7. 风险与缓解

| 风险 | 缓解 |
| --- | --- |
| 启动迁移阻塞服务 | 锁超时、语句超时、编排层健康检查摘流 |
| 多副本并发改表 | advisory lock + 迁移完成标记 |
| AutoMigrate 意外改类型 | 模型标签固定类型；CI parity；发布前 dry-run |
| 破坏性 SQL 无回滚 | 版本化 + 备份 + 先在 staging 演练 |
| 零值更新丢失 | 统一使用 map/Select 更新 |
| ORM 性能回退 | 热点基准 + `PrepareStmt` + 必要时 raw SQL |

| 31 个模型 + 43 个关联 | `internal/adapter/pg/gormmodel`（生成器 `contracts/tools/gen-gorm.mjs`） | AutoMigrate smoke：31 表 / 329 列 / 43 外键 / 9 个 CHECK |
| 启动迁移器 | `internal/adapter/pg/gorm.go`：advisory lock、lock/statement timeout、两阶段建表与外键 | 重复启动幂等；双副本并发测试通过 |

| 10 个原子函数 | `internal/store` 全部改为 GORM 事务与查询 | 限流、OTP 原子性、并发消费、状态检查、文档关联测试通过 |
| API 启动接入 | `cmd/api` 在连接 DB 前执行 AutoMigrate，失败即退出 | 构建通过；需 DB/Redis/模型环境做启动冒烟 |

说明：

- GORM AutoMigrate 分两阶段：先禁用外键建表，再补关联，解决环依赖与建表顺序。
- 业务查询不再使用 `Raw/Exec`；仅原子 CASE upsert 使用 `gorm.Expr`，清理/锁定使用 GORM 谓词与 `clause.Locking`。
- 测试建表与 TRUNCATE 仍使用测试 SQL；生产代码不依赖。
- 现有 pgx 仓储（会话/主体/档案/审计）尚未替换，后续按端点迁移。

剩余工作：

1. 将 pgx 仓储逐步迁移到 GORM 模型与 Repository。
2. 用真实 DB/Redis/模型做 API 启动冒烟与双副本起服验证。
3. 热点接口 pgx vs GORM 基准（门槛：不劣化 >10–15%）。
4. 外部破坏性 SQL 的版本化目录与演练。
