# 0001 Go版人脸核验服务 — 方案评估

> 需求清单：[0001-Go版人脸核验服务-需求清单.md](0001-Go版人脸核验服务-需求清单.md)
> 分支：`main`（目标仓库尚未初始化 Git） ｜ 日期：2026-11-14 ｜ 状态：已定稿，采用方案 A

## 1. 要解决的问题

在 Go 中复刻 .NET 版人脸核验服务的现有语义，同时满足“纯 Go ONNX 推理、无 cgo、无 `libonnxruntime`”的约束。难点不在 HTTP、存储或加密，而在三件事：

1. 是否存在能跑通 YuNet、SFace、MiniFASNetV2 的纯 Go ONNX 实现；
2. 图像预处理与后处理能否逐字节对齐 .NET 版，保证分数与动作判定不漂移；
3. 纯 Go 推理的性能与数值一致性是否可接受。

## 2. 约束事实与证据

### 2.1 模型算子盘点

对基线仓库 `models/` 的真实模型做 Protobuf 解析，得到 opset 与算子集合：

| 模型 | opset | 节点数 | 算子集合 |
| --- | --- | --- | --- |
| `face_detection_yunet_2023mar.onnx` | 11 | 106 | Add、Conv、MaxPool、Relu、Reshape、Resize、Sigmoid、Transpose |
| `face_recognition_sface_2021dec.onnx` | 11 | 88 | BatchNormalization、Conv、Dropout、Flatten、Gemm、Mul、PRelu、Sub |
| `2.7_80x80_MiniFASNetV2.onnx` | 11 | 104 | Add、BatchNormalization、Concat、Constant、Conv、Gather、MatMul、PRelu、Reshape、Shape、Unsqueeze |

模型输入输出名：

| 模型 | 输入 | 输出 |
| --- | --- | --- |
| YuNet | `input`，`[1,3,640,640]` | `cls_8/16/32`、`obj_8/16/32`、`bbox_8/16/32`、`kps_8/16/32` |
| SFace | `data`，`[1,3,112,112]` | `fc1`，128 维 |
| MiniFASNetV2 | `input`，`[1,3,80,80]` | `output`，3 类 logits |

### 2.2 纯 Go ONNX 实现现状

| 项目 | 实现方式 | 维护状态 | 对本项目模型的覆盖 |
| --- | --- | --- | --- |
| `oramasearch/onnx-go` + Gorgonia | 纯 Go 解释执行 | 2024-09 后无提交；Gorgonia 2023 年后基本停滞；官方后端测试通过率 27.6% | 缺 Resize、PRelu、Gather，三个模型均不可直接运行 |
| `AdvancedClimateSystems/gonnx` | 纯 Go，opset 13 子集 | 2025-03 后无提交 | 缺 MaxPool、Resize、BatchNormalization、Dropout，三个模型均不可直接运行 |
| `gomlx/onnx-gomlx` + `gomlx/gomlx` | ONNX 转 GoMLX 计算图；GoMLX 提供纯 Go 后端与 XLA 后端 | 活跃维护（2026-11-14 仍有提交） | 120 个算子，覆盖 YuNet 全部算子；缺 PRelu、Dropout |
| `purego` 系列（`onnxruntime-purego`、`pure-onnx`、`onnxruntime_purego`） | 无 cgo，但通过 `dlopen` 调用原生 `libonnxruntime` | 多个小项目维护 | 模型全覆盖；仍需随包分发 `.so/.dylib`，不满足“无原生库” |

### 2.3 性能证据

`onnx-gomlx` 官方 README 给出参考：同类纯 Go 实现（gonnx / onnx-go）在 BERT 句向量模型上约为 ONNX Runtime 的 1/8 速度；GoMLX 的纯 Go 后端在新版本中加入 SIMD 与多级并行，官方称在 Apple Silicon 上密集矩阵运算可达 2.51 TFlops/s，但未给出本项目 CNN 模型的公开数据。因此性能必须以本项目实测为准。

## 3. 候选方案

### 方案 A：onnx-gomlx + GoMLX 纯 Go 后端（采用）

- 通过 `onnx-gomlx` 解析 `.onnx`，转换为 GoMLX 计算图，设置 `GOMLX_BACKEND=go` 运行。
- 上游缺 PRelu、Dropout 两个算子。PRelu 可分解为 `max(x,0) + slope * min(x,0)`，Dropout 在推理期为恒等映射，补丁量小。
- 通过本地 `replace` 指向仓库内 `third_party/onnx-gomlx`，只增加这两个算子，不改动上游其它逻辑。
- 优点：无 cgo、无原生库、交叉编译简单、可构建单文件分发；上游活跃，长期可回归主干。
- 缺点：需要维护一个小补丁；CPU 性能低于 ONNX Runtime；数值一致性需逐模型验证。

### 方案 B：onnx-go + Gorgonia

- 纯 Go，但缺 Resize、PRelu、Gather；Gorgonia 与 onnx-go 均已停滞。
- 排除原因：无法加载现有模型，补齐算子与维护成本高于方案 A。

### 方案 C：gonnx

- 纯 Go，但缺 MaxPool、Resize、BatchNormalization、Dropout；仓库 2025-03 后无提交。
- 排除原因：三个模型均无法直接运行，补丁面大于方案 A。

### 方案 D：purego 绑定 ONNX Runtime

- 无 cgo，`CGO_ENABLED=0` 可编译，但运行时仍需 `libonnxruntime`。
- 排除原因：不满足“纯 Go / 无原生库”的约束；若后续方案 A 性能不达标，可作为退路。

### 方案 E：保留 cgo 绑定 ONNX Runtime

- 与基线数值最容易对齐，但引入 cgo 与原生库。
- 排除原因：与本次需求的核心约束冲突。

## 4. 采用方案与理由

采用方案 A，并设定明确退路：

1. 先在仓库内做引擎 spike：加载三个模型，补 PRelu/Dropout，输出张量形状与数值范围正确。
2. 用同一张测试图对比 Go 与 .NET 版的检测框、128 维特征、活体分数与动作几何量；相似度与阈值判定一致才进入完整工程。
3. 若纯 Go 后端在目标硬件上单帧延迟不可接受，或数值差异导致判定漂移，则退回方案 D（purego + ONNX Runtime），HTTP、存储、用例层不受影响。

理由：

- 只有方案 A同时满足“纯 Go”与“现有模型可运行”。
- 缺失算子可局部补齐，不需要重写模型或转换权重。
- 引擎通过接口隔离，退路切换不影响上层语义。

## 5. 风险与观察项

| 风险 | 影响 | 处置 |
| --- | --- | --- |
| GoMLX 上游 API 变动 | 编译失败或转换行为变化 | 锁定版本；补丁仓库内可审查；升级前跑数值回归 |
| PRelu/Dropout 补丁与上游冲突 | 升级成本 | 补丁保持最小；向上游提 PR |
| 纯 Go 后端性能不足 | 单帧延迟与吞吐上升 | spike 实测；不达标切方案 D |
| 图像缩放插值差异 | 检测框与分数轻微漂移 | 对齐双线性采样；用固定样本做容差回归 |
| 浮点累加顺序差异 | 特征余弦相似度小幅变化 | 对比同人/异人分数分布，不按位比较 |
| 模型许可证 | 分发合规 | 保留 MIT/Apache-2.0 声明，随模型分发 |

## 6. 复现方式

```bash
# 模型算子盘点（无第三方依赖，直接解析 Protobuf）
python3 /tmp/onnx_ops.py models/*.onnx

# 纯 Go 实现检索
gh search repos "onnx" --language=go --sort=stars --limit=30
gh api repos/gomlx/onnx-gomlx/contents/internal/onnxgomlx/graph.go --jq '.content' | base64 -d | grep -oE 'case "[A-Za-z]+"'

# GoMLX 纯 Go 后端
GOMLX_BACKEND=go go test ./internal/engine/...
```
